# Аудит швидкодії, SEO і доступності

**Практична робота:** ПР 9 «Тестування, оптимізація, SEO і доступність»
**Що перевірялося:** production-збірка React-клієнта (`npm run build` + `npm run preview`,
http://localhost:4173) з API на :3001. Сторінки: головна `/`, каталог `/recipes`,
рецепт `/recipes/borshch`.
**Інструменти:** Lighthouse 13.6 (Node API, режим **mobile** за замовчуванням: емуляція Moto G Power,
повільний 4G, CPU ×4), axe-core 4.14, Chrome DevTools Protocol (вкладка Issues), Chrome 157.
**Дата:** 15.11.2026.

|---|---|---|---|---|---|
| **LCP** (симуляція Lighthouse) | коли показано найбільший елемент | ≤ 2,5 с | 2,6 → **2,3 с** | 2,9 → 3,5 с | 2,5 → 2,6 с |
| LCP (реально виміряний у тому ж прогоні) | | | 0,29 → **0,15 с** | 1,41 → **0,21 с** | 0,35 → **0,17 с** |
| **CLS** | наскільки «стрибає» макет | ≤ 0,1 | 0 → **0** | 0–0,243 → **0** | 0,564 → **0** |
| **TBT** (лабораторна заміна INP) | час блокування головного потоку | ≤ 200 мс | 0 → 0–30 мс | 0–10 → **0 мс** | 0 → **0 мс** |
| **INP** (виміряно окремо, CPU ×4) | затримка відповіді на дію | ≤ 200 мс | тема — 64 мс | пошук < 16 мс, фільтр — 32 мс, перехід на рецепт — 32 мс | «+» порцій — 48 мс |
| FCP | перший вміст на екрані | ≤ 1,8 с | 1,5 → **0,8 с** | 1,5 → **0,8 с** | 1,5 → **0,8 с** |

**Чому LCP каталогу в симуляції зріс, а бал лишився ≥ 90.** Lighthouse не чекає повільного
мобільного інтернету насправді: він завантажує сторінку швидко, а потім *моделює* той самий
ланцюжок запитів на повільному 4G. Реально виміряний LCP каталогу зменшився в 6,7 раза
(1,41 → 0,21 с), бо зникло блокування від Google Fonts. Але симуляція тепер ставить у ту саму
вузьку смугу ще 4 файли шрифтів (~98 КБ) і фото, тож оцінка зросла до 3,5 с. Я перевірив по черзі:
без preload шрифтів, без латинських шрифтів, без `fetchpriority`, з preload запиту до API — LCP каталогу
в симуляції лишався 3,2–3,6 с. Справжня причина в іншому: фото першої картки браузер може почати
завантажувати лише після того, як JS виконався й отримав список рецептів від API. Так влаштований
клієнтський рендеринг (SPA). Прибрати цю затримку повністю можна лише рендерингом на сервері (SSR)
або попередньою генерацією HTML, а це за межами ПР 9.

## 3. Що змінено і чому

### 3.1 Швидкодія

| Зміна | Файли | Проблема в Lighthouse | Результат |
|---|---|---|---|
| Поки на сторінці є `aria-busy="true"` (лоадер), `main` займає щонайменше висоту екрана; `align-content: start` | `src/styles/app.css` | Layout shift: поки рецепт завантажувався, футер стояв одразу під лоадером, а потім «з'їжджав» вниз — CLS **0,564** (рецепт), **0,243** (каталог) | CLS **0** на всіх сторінках. Без правила каталог падає до 79 (перевірено, вимкнувши його в збірці) |
| Шрифти Lora і Manrope з власного сервера (`public/fonts/`, 4 woff2) замість Google Fonts | `src/styles/fonts.css`, `index.html` | Render-blocking: CSS з fonts.googleapis.com блокував перше малювання на ~870 мс, далі ще запити до fonts.gstatic.com | FCP 1,5 → **0,8 с** на всіх сторінках |
| `font-display: swap` | `src/styles/fonts.css` | Без нього текст невидимий, доки вантажиться шрифт | Текст видно одразу системним шрифтом |
| `<link rel="preload">` для кириличних шрифтів | `index.html` | Шрифт знаходився лише після розбору CSS | Перевірено: без preload головна гірша (LCP 3,2 с замість 2,8 с) |
| Preload фото борщу на головній (той самий `imagesrcset`/`imagesizes`, що в `<picture>`) | `index.html` | LCP-фото браузер знаходив лише після виконання JS | Фото вантажиться паралельно з JS |
| Preload запиту до API (`<link rel="preload" as="fetch">`) для головної, каталогу без фільтрів і рецепта; адресу API підставляє плагін у `vite.config.js` | `index.html`, `vite.config.js` | Ланцюжок HTML → JS → API → фото | Головна 96 → **99** (LCP 2,8 → 2,3 с). Дубля запиту немає — адреса точно збігається з `useFetch` |
| `fetchpriority="high"` для фото першої картки каталогу | `RecipeList.jsx`, `RecipeCard.jsx` | «fetchpriority=high should be applied» для LCP-фото | Підказку виконано (на симульований LCP не вплинуло, див. розділ 2) |
| **Lazy loading маршрутів:** `React.lazy` + `Suspense` для «Додати рецепт», «Редагування», «Контакти», 404 | `App.jsx`, `Layout.jsx` | Unused JavaScript ~33 КБ | Основний JS 239 → **218 КБ** (gzip 76 → 71 КБ); форми — окремі чанки 1–10 КБ. Головна, каталог і рецепт лишилися в основному файлі: з них починається візит, і зайвий запит за чанком лише затримав би LCP |
| Фото з ПР 5 вже мали WebP 480/800/1200, `width`/`height`, `loading="lazy"` поза першим екраном | — | — | Без змін; тест `RecipeCard.test.jsx` перевіряє ці атрибути |

**Кешування.** `vite preview` — локальний сервер для перевірки, і заголовки кешування на ньому
не налаштовуються. Lighthouse тут зауважень щодо кешу не мав. Файли в `dist/assets/` мають хеш у назві
(`index-D4JNzCBG.js`): після зміни коду змінюється назва, тому на хостингу (ПР 10) їм можна поставити
`Cache-Control: public, max-age=31536000, immutable`, а `index.html` — без довгого кешу.

### 3.2 SEO

| Що | Де | Деталі |
|---|---|---|
| Унікальні `title` і `meta description` | `hooks/usePageMeta.js`, усі сторінки | Перевірено на 9 адресах: усі title різні, description 48–167 символів |
| `<link rel="canonical">` | `usePageMeta` | Без параметрів пошуку: `/recipes?category=drinks` → `/recipes`, щоб комбінації фільтрів не вважалися дублікатами |
| `noindex` | сторінки 404, «рецепт не знайдено», редагування | Службові сторінки не потрапляють у пошук; canonical на них не ставиться |
| Open Graph і Twitter Card | `usePageMeta`, `index.html` | `og:title`, `og:description`, `og:type` (`article` для рецепта), `og:url`, `og:image` (фото рецепта JPG) |
| JSON-LD `Recipe` | `RecipeDetails.jsx` | Був з ПР 7; додано `image` (обов'язкове для розширеного результату Google), `url`, `author` |
| `robots.txt`, `sitemap.xml` | `public/`, генерує `npm run seo` (`scripts/generate-seo-files.js`) | 13 адрес: головна, каталог, 10 рецептів з `server/data/recipes.json`, контакти. До ПР 9 на `/robots.txt` сервер віддавав `index.html` — Lighthouse: «robots.txt is not valid, 30 errors» |
| `lang="uk"` | `index.html` | Було з ПР 7 |

**Адреса сайту.** Поки сайт не розміщено (ПР 10), у `sitemap.xml` і `robots.txt` стоїть
зарезервований домен `https://smak-tradytsii.example`, а canonical і `og:url` беруть адресу,
з якої відкрито сторінку. Після деплою: задати `VITE_SITE_URL` у `client/app/.env`
і виконати `SITE_URL=https://<адреса> npm run seo`.

**Обмеження SPA.** Google виконує JavaScript і бачить теги, які ставить `usePageMeta`.
Прев'ю в Telegram, Facebook і Viber будуються без JS, тож для них сторінка рецепта
матиме загальні OG-теги з `index.html`. Вирішує це лише SSR або попередній рендеринг.

| `aria-live` / `role="status"` / `role="alert"` | Лічильник «Знайдено N» у каталозі, підказки й статус порцій, `FormStatus` і `Notice` після дій, лоадер, помилка видалення |
| `alt` у всіх зображень | 0 `<img>` без `alt` на 9 адресах; декоративні мають `alt=""` |
