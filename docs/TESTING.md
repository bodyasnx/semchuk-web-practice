# Тестування

**Практична робота:** ПР 9 «Тестування, оптимізація, SEO і доступність»
**Автотести:** Vitest + React Testing Library (клієнт), `node:test` + `fetch` (API).
**Ручне тестування:** чек-лист із 15 кейсів за функціональними вимогами Ф1–Ф12 з [TZ.md](TZ.md).

## 1. Як запустити

```bash
npm test                      # з кореня: спершу тести API, потім тести клієнта
npm test --prefix server      # лише API (node --test)
npm test --prefix client/app  # лише клієнт (vitest run)
cd client/app && npm run test:watch   # Vitest у режимі спостереження під час розробки
```

## 2. Піраміда тестів у проєкті

| Рівень | Що перевіряє | Інструмент | Файли |
|---|---|---|---|
| Unit | Чисті функції без DOM і мережі: перерахунок порцій, валідація форм | Vitest | `client/app/src/utils/*.test.js` |
| Компонентні | Компонент у віртуальному DOM (jsdom) так, як його бачить людина: ролі, підписи, кліки | Vitest + React Testing Library + user-event | `client/app/src/components/recipes/*.test.jsx` |
| Інтеграційні (API) | Справжній Express-застосунок на випадковому порту, HTTP-запити, файл даних | `node:test` + вбудований `fetch` | `server/test/recipes.test.js` |
| Ручні / e2e | Повні сценарії в браузері: інтерфейс ↔ API ↔ файл | Chrome, чек-лист нижче | розділ 4 |

**Чому так:** найбільше тестів — на нижньому рівні, бо вони швидкі (24 тести за ~2 с) і точно
вказують, де помилка. Тести компонентів шукають елементи за роллю й підписом (`getByRole`,
`getByLabelText`), а не за класами — тож заодно перевіряють доступність: якщо в кнопки зникне
`aria-label`, тест упаде.

### 3.2 API (5 тестів)

Перед імпортом застосунку тест копіює `server/data/recipes.json` у тимчасову теку ОС і задає
`DATA_DIR` на неї (змінну підготовлено в ПР 8, `server/src/config.js`). Сервер слухає порт `0` —
ОС дає вільний, тож тести не конфліктують із запущеним `npm run dev`. Після тестів тека видаляється.
Останній тест перевіряє, що новий рецепт є в тимчасовій копії і **немає** в справжньому файлі.

| Тест | Очікування |
|---|---|
| `GET /api/recipes/borshch` | 200, рецепт з інгредієнтами |
| `GET /api/recipes?category=dumplings` | 200, усі рецепти — категорії `dumplings` |
| `GET /api/recipes/nope` | 404, `{ "error": "Рецепт не знайдено." }` |
| `POST /api/recipes` з `{}` | 400, `details` містить помилки для `title`, `category`, `servings`, `cookTime`, `difficulty`, `ingredients`, `steps` |
| `POST /api/recipes` з коректним тілом | 201, заголовок `Location: /api/recipes/<id>`, запис у тимчасовий файл, справжній не змінено |


**Помилки в консолі** були лише в TC-15, і вони очікувані: `net::ERR_FAILED` — запити, які тест
навмисно обірвав, і `404 (Not Found)` — відповідь API на неіснуючий рецепт (браузер завжди
журналює відповіді 4xx). В інших кейсах консоль порожня.

**Збої тестового скрипта (не сайту)**, знайдені під час підготовки прогону:
1. TC-11: поле «Базова кількість порцій» уже містить «4», і скрипт дописав «44» — сайт правильно
   показав «Введіть число від 1 до 20». Скрипт виправлено.
2. TC-12: форма редагування знову вимагає згоду на публікацію — це задумана поведінка
   (згоду підтверджують під час кожного збереження), скрипт додав клік.
3. TC-03, TC-15: скрипт брав текст не з того блоку (клас `card-grid__full` є і в заголовку
   результатів).
